### 10.4 A14 has a hole: check the SHA URL, not the branch URL

Found while re-verifying the above, and worth more than the verification itself.

After pushing the 10.3 correction (dev `c0d31fe8..7abd65ed`), the **branch-name**
raw URL still answered **HTTP 200 with 228,895 bytes** — the *previous*
revision — while the blob on `origin/dev` was already `ac48aea6…` at **229,575**
bytes. The **commit-SHA** URL returned 200 with 229,575, matching the blob and the
local file exactly:

```
raw…/vl/dev/…/2026-09-06-v5-precheck.md                 HTTP 200  228895   <-- STALE (CDN)
raw…/vl/7abd65ed…/…/2026-09-06-v5-precheck.md           HTTP 200  229575   <-- current
git ls-tree origin/dev …                        ac48aea6…          229575
wc -c (local)                                                      229575
```

`raw.githubusercontent.com` caches branch-name paths for roughly five minutes.
**So an A14 check against the branch URL can return 200 for a report revision that
no longer exists** — and, in the worst case, return 200 for a *file that was just
deleted*, or pass before the push has propagated at all.

**A14 amendment — OWNER-RULED AND LANDED.** The closeout fetch must pin the
**commit SHA** in the path, never a branch path, and must compare
`size_download` against `git ls-tree -r --long` for that blob. A bare 200 proves
only that something answered — the same defect this report documents 48 times
over in the product itself (§4.1: 48 of 102 panels fail silently), now found in
the audit protocol.
